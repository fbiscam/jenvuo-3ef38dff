# Shared business rules

- Customer-facing JX Bot daily target and drawdown copy must interpolate DAILY_TARGET_PCT and DAILY_DRAWDOWN_PCT from mt5-licenses.ts, not duplicate rates or display legacy fixed-dollar daily targets: keeps pricing, guides and AI knowledge aligned with server enforcement.
- Founding JX Bot access is decided by DB `founding_bot_check()` (hourly `process_founding_bot_milestones()`), mirrored in `founding-bot.ts` (tested), and the sidebar JX Bot lock uses the same `readPlan` result via `getJxBotNavAccess`: one rule for the EA validator, page and menu.
- A Founding trial plan ends at `trial_ends_at` in `process_founding_renewals()` with no grace and its `founding_trial_grant` credit is zeroed: the Founding month is a fixed term, not a renewal.
- Billing plan bullets come from `planFeatures` in `plan-features.ts` and the JX Bot page button from `jxBotAction` in `founding-bot.ts` (both tested): JX Bot is shown only to verified Founding members, others see Terminal + API credit.
- Plan prices live only in `plan-pricing.ts` (tested): Terminal + API price for everyone, plus the JX Bot cost for `isVerifiedFoundingMember`; pricing page, Payments and `applyPlanForPayment` all read it, and a paid plan runs JX Bot only for verified Founding members (`readPlan`, `checkBotByIp`): the DB `plans.price_usd` is not used for charging.
- Order approval credit is decided by `orderCreditToAdd` with `PLAN_API_CREDIT` (`plan-pricing.ts`, tested; DB `plans.wallet_usd` must match): plan orders add only the plan's API credit net of what `set_user_plan` already added, top-ups add the bought credit and never change the plan: the price also pays for Terminal/JX Bot access.
- Founding API credit comes from `FOUNDING_API_CREDIT` via `foundingCreditFor` (tested; DB `release_founding_credit()` must use the same amounts), added only by the admin Fund action (`updateFoundingApplication` approved->active, ID must be verified); Founding Terminal access needs a verified ID and ends 30 days after approval (`evaluateFoundingRow`, tested); seat limit/reopen date in `founding-seats.ts` (tested): one server path grants credit and access.
- Plan CTAs use `BuyNowButton`/`showBuyBlocked` (`src/components/BuyNowButton.tsx`): Apply now signed out, Buy now signed in, blocked toast (no modal, it shifts the page) until ID verified: one CTA rule everywhere.
- Founding form duplicates are decided by `foundingReapplyDecision` (`founding-reapply.ts`, tested) using server-key lookups: under-review blocks, rejected or account-removed applicants reopen, live/finished members are blocked; the form always answers the same "received" and the real status goes only by email (`already_applied`): the public form must not reveal who applied or is a member.
- Admin Email box (`/ops-x9k2-7m4n/emails`) sends one recipient per email through `sendAdminEmail` (`admin-email.functions.ts`, rules in `admin-email.ts`, tested) with the `admin-message` template; From is support@/sales@ on the verified sender domain and Reply-To is the matching @jenvu.com box, logged in `admin_sent_emails`: no bulk sends and replies go to the team inbox.
- Sign-out writes the ended session id into the shared `jenvu_signed_out` cookie; every jenvu.com address checks it on open and on tab focus via `decideSync` (`session-sync.ts`, tested) and drops a matching copy instead of re-sharing it: each address keeps its own browser session, so without the marker the homepage signed everyone back in.
- Ops Console new-item badges come from `opsPendingCounts` (`ops-counts.functions.ts`, ops-gate checked) and render with `OpsCount`; every admin tool is its own page at `/ops-x9k2-7m4n/<slug>` (slugs in `ops-tools.ts`, components in `src/components/ops/admin/`, wrapped in `OpsStandalone` which checks the console lock and restores the admin sign-in), old `/dashboard/admin/<slug>` links forward there, and `OpsPage` gives each the Support-inbox look (back button, title, theme/Lock tools, pill tab bar): admin tools never open inside the dashboard menu, one admin look.
- Timed browser refreshes skip hidden tabs (`pollWhileVisible`/`shouldPoll` in `poll.ts`, tested) and use realtime where it exists, with slow fallbacks; the EA report path does one license lookup and rewrites `last_validated_at` only via `licenseCheckDue` (5 min): the bot reports every minute, so per-call writes and fast polls were the main database load.
- Member-side Founding lookups (`getMyApplication` in `founding.functions.ts`) run server-side by user_id, then by the signed-in email, and link an unlinked row on the spot; approval also links it (`linkApplicationToUser`): RLS only shows linked rows, so just-approved members saw "No application found".
- Approved members (`ID_LOCK_APPLICATION_STATUSES`; pending/rejected applicants are never locked) with no verified ID get look-only dashboard pages (`idViewOnly`/`idActionsLocked` in `id-gate.ts`, tested; `IdViewOnly` wrapper) except the `ID_OPEN_PATHS`; key creation/rotation and Chat re-check server-side via `idActionBlock` (`id-gate.server.ts`); Payments allows top-ups before ID (`purchaseGate` kind) and refuses the active Founding trial plan (`isTrialPlanLocked`): UI blocks alone are bypassable.
- ID document uploads follow `doc-submission.ts` (tested): files register without changing status, `markMyDocumentsSubmitted` checks `submissionBlock` and sets "received"; after that members can't upload, view or delete (server + storage/table policies), reopening only on rejected/needs_info: submitted ID evidence must stay untouched.
- Ask Jenvu sends the core facts plus question-matched Help sections; `getRelevantJenvuKnowledge` budgets only the sections (tested in `ask-jenvu-knowledge.test.ts`): a shared budget let the long core facts crowd out every article.
- Plan display names come from the plan id in `getCreditState` (`credits.functions.ts`), not `plans.name`, and `ensureMt5License` moves existing JX Bot licenses to the current paid plan on every approved plan payment: a stale DB label showed Ultra accounts as Elite and upgraded users kept old-plan licenses.
