# Shared business rules

- Customer-facing JX Bot daily target and drawdown copy must interpolate DAILY_TARGET_PCT and DAILY_DRAWDOWN_PCT from mt5-licenses.ts, not duplicate rates or display legacy fixed-dollar daily targets: keeps pricing, guides and AI knowledge aligned with server enforcement.
- JX Bot is plan-based for every signed-in user: `botPlanFor` in `mt5-licenses.ts` (tested) picks paid plan, active Founding month (DB `founding_bot_check()`), else Free ($5/day, 1 IP via `FREE_BOT`); `readPlan` and `checkBotByIp` both use it and the sidebar uses `getJxBotNavAccess`: one rule for the EA validator, page and menu.
- A Founding trial plan ends at `trial_ends_at` in `process_founding_renewals()` with no grace and its `founding_trial_grant` credit is zeroed: the Founding month is a fixed term, not a renewal.
- Billing plan bullets come from `planFeatures` in `plan-features.ts` and the JX Bot page button from `jxBotAction` in `founding-bot.ts` (both tested): every plan lists JX Bot with its IPs and target; Free/Founding-month users see Upgrade.
- Plan prices live only in `plan-pricing.ts` (tested): one price per plan for everyone with JX Bot included; pricing page, Payments and `applyPlanForPayment` all read it: the DB `plans.price_usd` is not used for charging.
- Order approval credit is decided by `orderCreditToAdd` with `PLAN_API_CREDIT` (`plan-pricing.ts`, tested; DB `plans.wallet_usd` must match): plan orders add only the plan's API credit net of what `set_user_plan` already added, top-ups add the bought credit and never change the plan: the price also pays for Terminal/JX Bot access.
- Founding API credit comes from `FOUNDING_API_CREDIT` via `foundingCreditFor` (tested; DB `release_founding_credit()` must use the same amounts), added only by the admin Fund action (`updateFoundingApplication` approved->active, ID must be verified); Founding Terminal access needs a verified ID and ends 30 days after `founding_started_at` (set once by DB `start_founding_month()` when the ID is first verified; older rows fall back to approval; `evaluateFoundingRow`, tested); seat limit/reopen date in `founding-seats.ts` (tested): one server path grants credit and access.
- Plan CTAs use `BuyNowButton`/`showBuyBlocked` (`src/components/BuyNowButton.tsx`): Sign up (sign-up form) signed out, Buy now signed in; plans are open to everyone (`purchaseGate`, tested), only approved Founding members awaiting ID get the blocked toast, and credit top-ups are refused server-side (`no_topup`): plans only, one CTA rule everywhere.
- Founding form duplicates are decided by `foundingReapplyDecision` (`founding-reapply.ts`, tested) using server-key lookups: under-review blocks, rejected or account-removed applicants reopen only when signed in with that email (else the inbox gets the reapply note), live/finished members are blocked; the form always answers the same "received" and the real status goes only by email (`already_applied`): the public form must not reveal who applied or is a member.
- Admin Email box (`/ops-x9k2-7m4n/emails`) sends one recipient per email through `sendAdminEmail` (`admin-email.functions.ts`, rules in `admin-email.ts`, tested) with the `admin-message` template; From is support@/sales@ on the verified sender domain and Reply-To is the matching @jenvu.com box, logged in `admin_sent_emails`: no bulk sends and replies go to the team inbox.
- Sign-out writes the ended session id into the shared `jenvu_signed_out` cookie; every jenvu.com address checks it on open and on tab focus via `decideSync` (`session-sync.ts`, tested) and drops a matching copy instead of re-sharing it: each address keeps its own browser session, so without the marker the homepage signed everyone back in.
- Ops Console new-item badges come from `opsPendingCounts` (`ops-counts.functions.ts`, ops-gate checked) and render with `OpsCount`; every admin tool is its own page at `/ops-x9k2-7m4n/<slug>` (slugs in `ops-tools.ts`, components in `src/components/ops/admin/`, wrapped in `OpsStandalone` which checks the console lock and restores the admin sign-in), old `/dashboard/admin/<slug>` links forward there, and `OpsPage` gives each the Support-inbox look (back button, title, theme/Lock tools, pill tab bar): admin tools never open inside the dashboard menu, one admin look.
- Timed browser refreshes skip hidden tabs (`pollWhileVisible`/`shouldPoll` in `poll.ts`, tested) and use realtime where it exists, with slow fallbacks; the EA report path does one license lookup and rewrites `last_validated_at` only via `licenseCheckDue` (5 min): the bot reports every minute, so per-call writes and fast polls were the main database load.
- Member-side Founding lookups (`getMyApplication` in `founding.functions.ts`) run server-side by user_id, then by the signed-in email, and link an unlinked row on the spot; approval also links it (`linkApplicationToUser`): RLS only shows linked rows, so just-approved members saw "No application found".
- Approved members (`ID_LOCK_APPLICATION_STATUSES`; pending/rejected applicants are never locked) with no verified ID get look-only dashboard pages (`idViewOnly`/`idActionsLocked` in `id-gate.ts`, tested; `IdViewOnly` wrapper) except the `ID_OPEN_PATHS`; key creation/rotation and Chat re-check server-side via `idActionBlock` (`id-gate.server.ts`); Payments sells plans only (`purchaseGate` refuses top-ups) and refuses the active Founding trial plan (`isTrialPlanLocked`): UI blocks alone are bypassable.
- ID document uploads follow `doc-submission.ts` (tested): files register without changing status, `markMyDocumentsSubmitted` checks `submissionBlock` and sets "received"; after that members can't upload, view or delete (server + storage/table policies), reopening only on rejected/needs_info: submitted ID evidence must stay untouched.
- Ask Jenvu sends the core facts plus question-matched Help sections; `getRelevantJenvuKnowledge` budgets only the sections (tested in `ask-jenvu-knowledge.test.ts`): a shared budget let the long core facts crowd out every article.
- Plan display names come from the plan id in `getCreditState` (`credits.functions.ts`), not `plans.name`, and `ensureMt5License` moves existing JX Bot licenses to the current paid plan on every approved plan payment: a stale DB label showed Ultra accounts as Elite and upgraded users kept old-plan licenses.
- `installDomGuard` (`src/lib/dom-guard.ts`, run in `__root.tsx`) skips removeChild/insertBefore on moved nodes and the homepage loader waits at most 300ms for outside price feeds: ads/translate DOM edits and slow feeds made first opens fail until refresh.
- Invoice PDFs are built only by `buildInvoicePdf` in `invoice-pdf.ts` (layout of the reference invoice, site font from `public/fonts/invoice/` Latin subsets, vector Jenvu mark): one invoice look for every download.
- JX Bot saved `today_profit` is closed balance minus the UTC day's `start_balance` (`reportDayStart` in `mt5-licenses.ts`, tested), not the EA's figure: broker midnight resets wiped days.
- JX Bot 4.7% daily drawdown is measured from the day's peak closed balance (`peakDrawdown` in mt5-licenses.ts, tested; stored as `mt5_bot_reports.peak_balance`) on both server and EA: protects profit already closed that day.
- Dashboard pages that load lists on open paint the last per-user snapshot from `page-cache.ts` first, then refresh in the background: avoids a blank "Loading" on every visit.
- News Impact (`/dashboard/news`): real US release results from the TradingView calendar and measured reactions (Binance 5m PAXG/EURUSDT, Yahoo hourly GBPJPY/DXY) are stored once in `news_releases` by `news-impact.server.ts`, a few releases per page call; the page is one next-news section (countdown, last-hour pre-news banner via `inPreNewsWindow`, beat/miss UP-DOWN cards) whose reads come only from those stored reactions via `news-impact.ts` (tested): no invented history and few outbound requests per call.
- Google/Apple sign-ups run the email sign-up abuse checks and the free trial right after the session exists (`completeSocialSignup` → `finishSocialSignup` in `custom-auth.server.ts`, new-account rule `isFreshSocialSignup` in `social-signup.ts`, tested); a refused brand-new social account is deleted server-side: the provider creates the account before app code runs, so the checks can't happen earlier.
- Chat replies run as `chat_jobs` rows: `playgroundChat` (with `jobId`) keeps working via `keepAlive` (`src/lib/keep-alive.server.ts`, Workers `waitUntil` captured in `src/server.ts`) and saves the result; the page keeps the pending id in browser storage and polls `getChatJob` on return; Stop calls `stopChatJob` (stopped replies are not charged): replies survive leaving the page.
- Blog articles reach Google by resubmitting `https://jenvu.com/sitemap.xml` through the Search Console connector (`submitToGoogle` in `generate-insight.ts`), once per run: the per-URL Indexing API returns 404 through the connector.
- API keys per plan live in `PLAN_API_KEYS` (`free-plan.ts`, tested) and DB `plans.extension_key_limit` must match; the server enforces the DB value: pricing copy and key creation agree.
- API per-minute caps and daily token ceilings per plan live only in `plan-entitlements.ts` (`PLAN_API_RPM`, `PLAN_DAILY_TOKEN_LIMITS`, tested in `free-trial.test.ts`) and are enforced in `getExtensionEntitlement` for every plan: pricing, docs and help read or mirror one source.
- Password sign-in always runs on the server (`passwordSignInWithSecondStep`): with email codes on (`account_email_2fa`) the fresh session is ended and a `second_step` code is emailed, the session opens only in `finishPasswordSignInWithCode` and is recorded in `email_2fa_sessions`; the dashboard guard (`owesEmailCode` in `_authenticated/route.tsx`, rule `needsEmailSecondStep` in `two-factor.ts`, tested) signs out password sessions that skipped it. One-time code sign-in (`codeSignIn`) and Google sessions count as email-proven. Removing email codes or the authenticator, and email changes, are refused server-side for 24h after a new-device `login_events` row (`readSecurityHold`): the browser can't skip the code or the hold.
- Community photos and post media are served only through `/api/community-media` tokens (`community-media-token.server.ts`), which re-check blocks and post deletion on every load; mail signs only the viewer's own avatar: long-lived storage links outlived blocks.
- Plan orders are priced on the server (`createTopupOrder` uses `planPrice`, ignoring the browser amount) and approval starts a plan or adds its API credit only when `planOrderCovers` (`plan-pricing.ts`, tested) says the payment covers it: a client-set amount once let an underpaid order collect plan credit.
- The first sign-up step (`createSignupOtp`) refuses a confirmed address with `signupEmailBlock` (`signup-guard.ts`, tested) before any code is made; Turnstile guards that step: owner wants a clear already-registered error.
